Q1 (a) — Define Strong AR, Weak AR, Spatial Display Model [5 marks]
• Strong AR: Digital content is tightly integrated with the real world; virtual objects interact with and respond to the
physical environment in real time. E.g., HoloLens overlaying holograms that are spatially anchored to real surfaces.
[1.5]
• Weak AR: Digital content is loosely overlaid on reality without deep environmental integration. E.g., Snapchat face
filters that overlay graphics on camera feed but don't understand 3D space. [1.5]
• Spatial Display Model: Uses projectors and spatial surfaces to display AR content without head-worn devices.
Includes Projection Mapping / Spatial Augmented Reality — projecting digital imagery onto irregularly shaped objects
to create illusions. E.g., Sony's Spatial Reality Display reproducing 3D images viewable by naked eye. [2]
PPT Ref: Unit 1, Slides 21–24 (Spatial Reality Display, Projection Mapping)
────────────────────────────────────────────────────────────────────────────────────────────────────
Q1 (b) — Immersion vs Presence in VR [5 marks]
• Immersion: The objective, measurable degree to which a VR system engages the user's senses — determined by
hardware capabilities (display resolution, FOV, tracking accuracy, frame rate). A technical property of the system. [2]
• Presence: The subjective psychological feeling of 'being there' in the virtual world. Depends on immersion + content
quality + user engagement. A user experience measure. [2]
• Significance: High immersion doesn't guarantee presence (poor content can break it). VR designers must optimize
both — hardware (immersion) AND content/interaction design (presence) to create believable experiences. [1]
PPT Ref: Unit 2, Slides 6–7 (Believable, Interactive, Explorable, Immersive)
────────────────────────────────────────────────────────────────────────────────────────────────────
Q1 (c) — Input.GetKey() variants in Unity [5 marks]
• Input.GetKey(KeyCode.W): Returns true EVERY frame the key is held down. Use: continuous movement —
character moves forward as long as W is pressed. [1.5]
• Input.GetKeyDown(KeyCode.Space): Returns true ONLY on the first frame the key is pressed. Use: single actions
like jumping or shooting — triggered once per press. [1.5]
• Input.GetKeyUp(KeyCode.E): Returns true ONLY on the frame the key is released. Use: actions like releasing a
grabbed object or ending an interaction. [1]
• Example code concept: In Update(), use Input.GetKey for WASD movement with transform.Translate(), and
Input.GetKeyDown for jump with Rigidbody.AddForce(). [1]
PPT Ref: Unit 3, Scripting Fundamentals — object interaction and movement

Q1 (d) — Marker-based vs Markerless AR Tracking [5 marks]

• Marker-based: Uses predefined visual markers (images/patterns) that the camera recognizes to anchor virtual content.
Platform example: Vuforia image targets. Advantages: reliable, accurate placement, works well indoors. Limitations:
needs pre-printed markers, limited to marker locations. [2.5]
• Markerless: Uses device sensors and environment features (plane detection, feature points, SLAM) to place content
anywhere. Platform example: ARFoundation with ARCore/ARKit. Advantages: no markers needed, flexible placement
anywhere. Limitations: needs well-lit textured surfaces, less precise in featureless areas. [2.5]

Q2 (a) — [SerializeField] vs public in Unity [10 marks]
• [SerializeField]: A C# attribute that exposes a private variable in the Unity Inspector without making it accessible to
other scripts. Preserves encapsulation. [2]
• public: Makes variable accessible both in Inspector AND from other scripts. Less encapsulated — any script can
modify it. [2]
• Key difference: [SerializeField] private float speed = 5f; → visible in Inspector, hidden from other scripts. public
float speed = 5f; → visible everywhere. [2]
• When to use [SerializeField]: Designer-tweakable values (speed, health, colors) that shouldn't be modified by other
scripts at runtime. Best practice for most cases. [2]
• When to use public: When the variable genuinely needs to be accessed/modified by other scripts (e.g., a health value
that the damage system needs to reduce). [2]
PPT Ref: Unit 3, C# scripting fundamentals — variables and inspector visibility
────────────────────────────────────────────────────────────────────────────────────────────────────
Q2 (b) — Unity GameObject Lifecycle Methods [10 marks]
• Awake(): Called once when the script instance is loaded (before Start). Execution order: first. Use: initializing
references, setting up singleton patterns. Runs even if script is disabled. [2.5]
• Start(): Called once before the first Update, only if the script is enabled. Use: initialization that depends on other
objects being Awake'd first (e.g., accessing components set up in Awake of other scripts). [2.5]
• Update(): Called once per frame. Frame-rate dependent. Use: handling input, non-physics movement, UI updates,
game logic that needs to run every frame. [2.5]
• FixedUpdate(): Called at fixed time intervals (default 0.02s). Frame-rate independent. Use: physics calculations,
Rigidbody forces, consistent physics behavior regardless of FPS. [2.5]
PPT Ref: Unit 3, Scripting Fundamentals — execution order and object interaction

Q3 (a) — Plane Detection in ARFoundation [10 marks]
• AR Session: The core component that manages the AR lifecycle. Must be in scene for any AR functionality. [1.5]
• AR Camera: Replaces the default camera; renders the real-world camera feed as background and overlays virtual
content. [1.5]
• AR Plane Manager: Component that enables plane detection. Detects horizontal planes (floors, tables) and vertical
planes (walls). [2]
• How it works: Device camera captures environment → ARFoundation identifies flat surfaces using feature point
analysis → generates plane meshes → fires events (planeAdded, planeUpdated) that scripts can listen to. [2.5]
• Object placement: Once planes are detected, use AR Raycast Manager to cast rays from screen touch position → if
ray hits a plane, Instantiate() a 3D object at the hit point → object appears on the real surface. [2.5]
PPT Ref: Unit 4, Pages 19–23 (Plane Detection, Feature Points, Spatial Mapping)
────────────────────────────────────────────────────────────────────────────────────────────────────
Q3 (b) — AR Anchors and Spatial Persistence [10 marks]
• AR Anchor: A component that locks a virtual object to a specific point in the real world's coordinate system. The
anchor maintains the object's position even as the device moves. [3]
• World Coordinate System: ARFoundation establishes a coordinate system relative to the device's starting position.
All virtual objects are positioned using this system. [2]
• How anchors maintain persistence: When an anchor is created at a detected plane point, ARFoundation continuously
updates its transform relative to the real world using SLAM tracking → even as the user walks around and comes back,
the anchored object stays in place. [3]

Q4 — VR Training Simulator — Scenario Answer [20 marks]
(a) System Architecture [7 marks]
• Hardware: Meta Quest 2/3 or HTC Vive (standalone or tethered). Controllers for hand interaction. Justification:
widely available, good tracking. [2]
• Unity project: Organized into folders — Scenes/Models/Scripts/Audio/UI. Separate scenes per training module. [1.5]
• VR Camera Rig: XR Rig (Unity XR Interaction Toolkit) or OVRCameraRig (Oculus). Provides head tracking +
controller tracking. [1.5]
• VR SDK choice: Unity XR Interaction Toolkit — cross-platform, supports multiple headsets, built-in grab/ray
interaction. [2]
(b) Implementation [8 marks]
• Machinery interaction: XR Ray Interactor for pointing at machine parts + XR Grab Interactable for grabbing
levers/buttons. Each interactable triggers corresponding machine state changes. [3]
• Training module progression: State machine (idle → tutorial → practice → assessment). UI panels in world-space
Canvas show current step. Checkpoints validate correct actions. [2.5]
• Performance tracking: Track metrics — time per task, errors made, steps completed. Display results on a VR
scoreboard (world-space Canvas) at the end of each module. [2.5]
(c) Challenges [5 marks]
• Motion sickness: Use teleportation locomotion instead of smooth movement. Fixed reference points. Maintain 72+
FPS. [2]
• Haptic simulation: Controller vibration patterns for different interactions (heavy lever = strong vibration). Audio
feedback compensates for lack of physical resistance. [1.5]
• Training effectiveness: Pre/post knowledge tests. Compare VR-trained vs traditionally-trained worker performance.
Track error rates over time. [1.5]

Q5 — AR Furniture Placement — Scenario Answer [20 marks]
(a) AR System Design [7 marks]
• ARFoundation with ARCore (Android) + ARKit (iOS). Cross-platform from single Unity project. [1.5]
• Required components: AR Session (lifecycle), AR Camera (camera feed + tracking), AR Plane Manager
(floor/surface detection), AR Raycast Manager (touch-to-world raycasting). [3]
• Environmental understanding: Plane detection identifies horizontal surfaces (floors, tables). Feature points track the
environment. Device builds spatial map for accurate placement. [2.5]
(b) Placement Mechanism [8 marks]
• Surface detection: AR Plane Manager detects horizontal planes → visual feedback (grid overlay) shows detected
surface to user. [2.5]
• Object instantiation: User taps screen → AR Raycast from touch position → if hits detected plane →
Instantiate(furniturePrefab, hitPose.position, hitPose.rotation) → furniture appears on surface. [3]
• Gesture handling: Touch drag → update object position via raycasting. Two-finger pinch → scale. Two-finger rotate
→ rotate around Y-axis. Implemented via Touch input in Update(). [2.5]
(c) Realism and UX [5 marks]
• Light estimation: ARFoundation's AR Light Estimation Manager estimates ambient light intensity and color
temperature → apply to virtual furniture's lighting to match room. [2]
• Shadow rendering: Transparent shadow-receiving plane placed at detected surface level. Directional light casts
shadows from furniture onto this invisible plane. [1.5]
• Occlusion: AR Occlusion Manager uses depth data (LiDAR on iOS) to hide furniture parts behind real objects. On
non-LiDAR devices, use plane-based occlusion. [1.5]

Q6 (a) — VR Locomotion Techniques [15 marks]
~3.5 marks per technique + 1 mark for recommendation
• Teleportation: Point controller → show arc/target → release to teleport. Pros: zero motion sickness, intuitive. Cons:
breaks immersion, non-continuous movement. Best for: casual VR, users prone to sickness. [3.5]
• Smooth locomotion: Joystick-based continuous movement like traditional FPS. Pros: fluid, familiar to gamers. Cons:
high motion sickness risk. Best for: VR gamers, action experiences. [3.5]
• Arm-swinging: Mimics walking by swinging arms with controllers. Pros: physical, more immersive than
teleportation. Cons: tiring, moderate sickness risk. Best for: fitness/exercise VR. [3.5]
• Room-scale walking: Physical walking within tracked play area. Pros: most natural, zero sickness. Cons: limited to
physical space size. Best for: small-area experiences, exhibitions. [3.5]
• Recommendation for VR museum tour: Teleportation — visitors of all ages, comfort levels; long session duration;
exploratory not action-oriented; zero sickness risk. [1]

Q6 (b) — Performance Optimization Strategies [5 marks]
• LOD (Level of Detail): Reduce polygon count for distant objects. Major FPS impact — fewer vertices to render.
Critical for mobile AR. [1.7]
• Occlusion Culling: Don't render objects hidden behind other objects. Reduces draw calls significantly. Unity's built-
in occlusion culling system. [1.7]
• Texture Compression & Atlas: Compress textures for target platform (ASTC for mobile). Combine multiple textures
into atlases to reduce draw calls. Reduces memory + GPU load. [1.6]
PPT Ref: Unit 5, Page 23 (Performance: LOD, Occlusion culling)
────────────────────────────────────────────────────────────────────────────────────────────────────
Q7 — MR Remote Collaboration — Scenario Answer [20 marks]
(a) MR Architecture [7 marks]
• Dual-mode system: AR mode (mobile — ARFoundation) renders shared 3D model on user's desk. VR mode (headset
— XR Rig) provides full-scale immersive view of same model. [2.5]
• Consistent 3D representation: Single canonical model stored on server. Both AR and VR clients receive same
mesh/material data. AR scales down; VR renders at full scale. [2]
• Networking: Photon PUN/Fusion or Mirror for real-time sync. Room-based multiplayer — all participants join same
room. State sync via RPCs and networked transforms. [2.5]
(b) Synchronization [8 marks]
• Object transform sync: NetworkTransform component syncs position/rotation/scale. Owner sends updates; others
interpolate. Delta compression reduces bandwidth. [3]
• User avatars: Each user represented by avatar showing head position (from HMD tracking) and hand/pointer direction
(from controllers or touch). Color-coded per user. [2.5]
• Bandwidth optimization: Only sync changed transforms. Use reliable channel for critical state (object
creation/deletion) and unreliable for frequent updates (position). Compress float data. [2.5]
(c) Usability [5 marks]
• Spatial alignment: Define shared origin point. AR uses detected surface as anchor; VR uses fixed world origin.
Calibration step aligns both coordinate systems to same reference. [2]
• Mobile performance: LOD for complex models on mobile. On-demand loading of model details. Simplified shaders
for AR mode. [1.5]
• Interaction parity: AR users use touch for rotate/scale/annotate. VR users use controller grab/point. Both map to same
underlying actions — input abstraction layer. [1.5]
PPT Ref: Unit 6 (MR definition, combined AR+VR); Unit 4 (VR interaction design)

Q2 (a) — OnCollisionEnter() vs OnTriggerEnter() [10 marks]
• OnCollisionEnter(Collision col): Called when two colliders physically collide. Both objects need colliders; at least
one needs Rigidbody. Physics forces are applied — objects bounce/stop. [3]
• OnTriggerEnter(Collider other): Called when a collider marked as 'Is Trigger' overlaps another. No physics response
— objects pass through each other. Used for detection zones, pickups, etc. [3]
• Rigidbody component: Required for physics simulation. Properties — Mass (weight), Drag (air resistance), Angular
Drag (rotation resistance), Use Gravity (enable/disable). Makes object respond to forces. [2]
• When to use: Collision → physical interactions (ball hitting wall, player landing on ground). Trigger → detection
without physics (entering a room, collecting a coin, hazard zone detection). [2]
