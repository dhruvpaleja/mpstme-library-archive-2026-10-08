b.   Assess the role of Kubernetes Pods within a cluster model. Why are
Pods considered a foundational unit instead of individual containers?
2 MARKS EACH POINT
Pod is the smallest deployable unit in Kubernetes, not a container.
That design choice is deliberate – it solves problems that single
containers can’t handle alone.
Role of Pods within the Kubernetes cluster model
Pods sit between containers and higher-level controllers like
Deployments, ReplicaSets, and DaemonSets. Here’s how they fit:
1. Atomic unit of scheduling
The kube-scheduler never places individual containers on nodes. It
places whole Pods. All containers in a Pod are guaranteed to land on
the same node, run or fail together, and share the same lifecycle. This
makes scheduling decisions simpler and more predictable.
2. Shared execution environment
Every container in a Pod shares:   10
(CO2 / BL3)
• Network namespace: One IP address per Pod. Containers talk to M
each other via localhost, just like processes on a VM. No need for
inter-container service discovery.
• Storage volumes: Mounted volumes are available to all containers
in the Pod, enabling sidecar patterns.
• UTS, IPC namespaces: They can share hostname and inter-
process communication if configured.
3. Scaling and replication boundary
Horizontal Pod Autoscalers, ReplicaSets, and Deployments scale Pods,
not containers. If you need 3 copies of an app, you get 3 Pods. That
keeps scaling logic clean – you’re not trying to reason about scaling
individual containers inside a shared host.
4. Resource and policy boundary
Resource requests/limits, node affinity, tolerations, and security
contexts are applied at the Pod level. The kubelet manages the Pod as a
single entity for health checks, restart policy, and termination grace
periods.
********** 6 **********
--- page 7 ---
Why Pods are foundational instead of containers
Kubernetes could have made containers the base unit, but containers
alone are too granular for real-world apps. Pods model the “logical
host” concept.

a.   Describe the disadvantages of containers.
2 mark each( any 5)
1. Weaker isolation than VMs
Containers share the host OS kernel. A kernel vulnerability
or breakout can impact all containers on that host, unlike
VMs that have separate kernels via a hypervisor.   10M
(CO4 / BL4)   2. Persistent storage complexity
Containers are ephemeral by design. Managing stateful data
requires external volumes, storage drivers, and
orchestration. Data persistence isn’t built-in like with VMs.
3. Networking overhead and complexity
Overlay networks, service meshes, and ingress/egress rules
add latency and operational complexity. Cross-host
container networking is harder than VM networking.
4. Security surface area
Default container images often run as root and may include
********** 9 **********
--- page 10 ---
unnecessary packages. Misconfigured privileges, excessive
capabilities, or unpatched base images increase risk.
5. Monitoring and debugging is harder
A single host can run hundreds of containers. Logs, metrics,
and traces are distributed. You need extra tooling like
Prometheus, Fluentd, or eBPF to get visibility.
6. Not ideal for all workloads
Monolithic apps with heavy IPC, apps needing specific
kernels, Windows licensing, or GUI-based workloads often
run better in VMs. GPUs and specialized hardware can be
tricky to share.
7. Image and sprawl management
Container sprawl, version drift, and large image layers lead
to storage bloat. You need registries, scanning, and lifecycle
policies to manage it.
8. Shared kernel limits OS diversity
All containers on a Linux host must use Linux. You can’t run
a Windows container on a Linux kernel, unlike VMs where
each guest OS is independent.
9. Resource contention
Without proper CPU/memory limits, noisy neighbor
containers can starve others because they share the host’s
scheduler and memory.
10. Learning curve and ecosystem complexity
Running containers in production means Kubernetes, Helm,
service mesh, GitOps, etc. The tooling stack is powerful but
heavy compared to just spinning up a VM.

2 MARKS EACH POINT
Pod is the smallest deployable unit in Kubernetes, not a container.
That design choice is deliberate – it solves problems that single
containers can’t handle alone.
Role of Pods within the Kubernetes cluster model
Pods sit between containers and higher-level controllers like
Deployments, ReplicaSets, and DaemonSets. Here’s how they fit:
1. Atomic unit of scheduling
The kube-scheduler never places individual containers on nodes. It
places whole Pods. All containers in a Pod are guaranteed to land on
the same node, run or fail together, and share the same lifecycle. This
makes scheduling decisions simpler and more predictable.
2. Shared execution environment
Every container in a Pod shares:   10
(CO2 / BL3)
• Network namespace: One IP address per Pod. Containers talk to M
each other via localhost, just like processes on a VM. No need for
inter-container service discovery.
• Storage volumes: Mounted volumes are available to all containers
in the Pod, enabling sidecar patterns.
• UTS, IPC namespaces: They can share hostname and inter-
process communication if configured.
3. Scaling and replication boundary
Horizontal Pod Autoscalers, ReplicaSets, and Deployments scale Pods,
not containers. If you need 3 copies of an app, you get 3 Pods. That
keeps scaling logic clean – you’re not trying to reason about scaling
individual containers inside a shared host.
4. Resource and policy boundary
Resource requests/limits, node affinity, tolerations, and security
contexts are applied at the Pod level. The kubelet manages the Pod as a
single entity for health checks, restart policy, and termination grace
periods.

Kubernetes could have made containers the base unit, but containers
alone are too granular for real-world apps. Pods model the “logical
